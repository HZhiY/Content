## 一、核心资料结论

1. **产品形态的本质**：网页（含 H5）、小程序、公众号、App 是不同层级的「触达用户方式」；它们共享「解决用户需求」的目标，但在运行环境、发布流程、能力开放、维护成本上差异显著。来源：微信《小程序产品定位及功能介绍》；微信公众号平台协议（二手归纳）。
2. **网页/H5**：基于 Web 标准（HTML/CSS/JS）的页面，可在浏览器、App 内 WebView、小程序 web-view 等环境打开；静态网页适合展示型、工具页、落地页等场景，部署与迭代相对灵活。来源：GitHub Pages 文档；Vite《部署静态站点》（二手材料）。
3. **微信小程序**：在微信内运行、无需安装即可使用的轻量应用；需注册账号、选择服务类目、提交代码审核后手动发布；个人主体可注册但开放类目受限，且暂不支持微信认证与微信支付。来源：微信《小程序产品定位及功能介绍》；微信开放社区注册上限说明。
4. **微信公众号**：微信公众平台下的账号形态，分订阅号与服务号；侧重信息传播与业务服务，不是完整「产品容器」；个人可注册订阅号，服务号传统上偏企业主体（待核个人服务号新规则）。来源：微信公众号平台协议；微信《公众号介绍》。
5. **原生 App**：基于 iOS/Android 系统开发、需安装使用的应用；上架分发通常需开发者账号（Apple Developer Program 年费 99 美元/中国大陆约 ¥688；Google Play 一次性注册费 25 美元），并承担多端开发、审核、迭代维护成本。来源：Apple Developer Program 官网；Google Play 费用说明（二手聚合，待核 Google 官方最新页面）。
6. **网页 vs 小程序（第一款常见纠结）**：网页跨环境投放更灵活、更新通常无需平台审核；小程序依赖微信生态、触达与分享便利，但每次发布需微信审核，且个人主体有类目与支付限制。来源：微信《小程序产品定位及功能介绍》；阿里云开发者社区 H5 与小程序对比文（二手材料）。
7. **轻量验证路径**：MVP（最简可行产品）强调用最低成本验证核心假设；表单/问卷类工具（如腾讯问卷、金数据等）可用于收集意向、预约、报名类需求信号，但不等于替代完整产品。来源：Atlassian MVP 指南（二手材料）；人人都是产品经理 MVP 文章（二手材料）。
8. **复杂度陷阱（定性）**：登录系统、支付、多端同步、后台管理、审核合规等会显著抬高第一款产品的开发与维护成本；个人开发者第一款产品宜先验证「是否有人要」，再扩展形态与功能。来源：系列总计划边界；01MVP 手册（二手材料）；待后续事实核查补具体政策口径。

## 三、分主题资料整理

### 3.1 网页/H5 是什么及适合什么

#### 基本资料

- 「H5」在中文语境常指移动端网页，技术本质是 HTML/CSS/JavaScript 等 Web 标准页面，可在浏览器中打开。来源：慕课网 FinClip 科普文（二手材料）；阿里云开发者社区问答（二手材料）。
- 网页运行环境包括：手机/PC 浏览器、App 内 WebView、小程序提供的 web-view 组件等；不依赖单一超级 App。来源：慕课网 FinClip 科普文（二手材料）。
- GitHub Pages：可将 GitHub 仓库转为线上网站，适合展示开源项目、博客、简历等，无需单独购买传统主机（仍可能需要自定义域名等）。来源：GitHub Pages 文档（https://docs.github.com/zh/pages）。
- 静态站点：构建时生成 HTML/CSS/JS 文件，部署后无需服务端动态渲染；适合落地页、文档站、作品集、简单工具页等。来源：Vite《部署静态站点》（二手材料）；腾讯云开发者社区静态站生成器文章（二手材料）。
- 网页/H5 更新通常由开发者自行部署新版文件即可，一般不经过应用商店或微信平台的内容审核（但若内容违规仍可能被封禁或下架，待核具体机制）。来源：有赞电商资讯文（二手材料）；慕课网 FinClip 科普文（二手材料）。

#### 口径差异

- 口径 A（技术向）：H5 = Web 页面，跨浏览器运行。来源：阿里云开发者社区（二手）。
- 口径 B（产品向）：「网页产品」= 用户通过 URL 访问的服务，含静态站、SPA、后端 API 驱动的 Web App。来源：行业归纳（二手，待核）。
- 当前建议：条目 01 用「通过链接打开的网页」白话解释，静态站作为个人开发者常见子类型点到为止；不展开前后端架构教程。

#### 可用于正文的解释

- 网页适合：展示信息、简单工具、落地页、等待名单、作品集、轻量表单嵌入页等「通过链接就能访问」的场景。
- 网页不太适合（第一款角度）：强依赖手机系统能力、离线复杂交互、需要应用商店分发信任背书的场景（待大纲界定）。

#### 风险提示

- 国内访问静态站仍可能涉及域名、备案、HTTPS 等基础设施（本主题包不展开，避免与栏目 02 重复跑题）。
- 「H5」不是严谨技术标准名称，正文宜用「网页」为主。

### 3.2 微信小程序是什么及适合什么

#### 基本资料

- 官方定义：微信小程序是一种全新的连接用户与服务的方式，可在微信内被便捷地获取和传播，同时具有出色的使用体验。来源：微信《小程序产品定位及功能介绍》（https://developers.weixin.qq.com/miniprogram/introduction/index.html）。
- 小程序运行环境：微信 App 内；用户可通过搜索、扫码、分享等方式打开，无需单独安装。来源：同上；微信《小程序简介》（二手背景材料）。
- 注册流程概要：注册小程序账号 → 选择主体类型 → 完善信息 → 开发 → 上传代码 → 提交审核 → 审核通过后手动发布。来源：微信《小程序产品定位及功能介绍》第三章「代码审核与发布」。
- 主体类型包括个人、企业、政府、媒体等；个人主体范围：18 岁以上有国内身份信息的微信实名用户。来源：同上第一章。
- 个人主体小程序开放服务类目须查阅官方「个人主体小程序开放的服务类目」文档；开发前必须确认类目是否开放。来源：同上第二章 2.3。
- 个人类型账号暂不支持微信认证；已认证账号（企业等）可申请微信支付。来源：同上第四章、第五章。
- 注册数量上限（微信开放社区官方说明）：同一身份证注册个人类型小程序数量上限为 5 个；同一邮箱只能申请 1 个小程序。来源：微信开放社区帖（https://developers.weixin.qq.com/community/develop/doc/000484159a0308e4ffcf942ca56c00）。
- 审核：管理员在版本管理提交审核；审核通过后需开发者手动点击发布；首次提交可能因缺少测试账号等被打回。来源：微信《小程序产品定位及功能介绍》3.1–3.2。
- 企业主体微信认证费用：300 元（认证通过前部分功能暂无法使用）。来源：微信官方注册流程说明。

#### 口径差异

- 口径 A（官方）：小程序是微信内连接用户与服务的方式，体验接近原生。来源：微信官方文档。
- 口径 B（行业）：小程序 = 轻量 App，适合交易、预约、工具、内容服务等。来源：多个行业科普站（二手，营销色彩重）。
- 当前建议：正文以官方定位+开放类目+审核发布流程为硬边界；行业场景举例须克制，避免写成「万能容器」。

#### 可用于正文的解释

- 小程序适合：目标用户主要在微信内、需要分享裂变、要用微信登录/支付/消息能力、功能边界在开放类目内的产品。
- 小程序不太适合：必须独立于微信运行、强依赖短信链接直达、个人主体做不了的目标类目、需要频繁静默更新且不能等待审核的场景。

#### 风险提示

- 个人主体类目限制是常见卡点；二手文章反映日记、记事、部分「管理」类名称易被拒（待核最新类目政策）。来源：dev-zuo 博客（二手材料）。
- 不要把「注册小程序」写成「产品已上线」；审核与发布是必要步骤。
- 企业认证 300 元、审核时长等数字会变化，正文引用须以事实核查为准。

### 3.3 微信公众号是什么及适合什么

#### 基本资料

- 微信公众平台协议：微信公众账号分为订阅号、服务号、小程序和企业号；公众号旨在为媒体和个人提供信息传播方式，构建与读者沟通管理模式。来源：微信公众平台服务协议（https://mp.weixin.qq.com/cgi-bin/readtemplate?t=home/agreement_tmpl&type=info&lang=zh_CN）。
- 微信官方文档（公众号）：公众号是用户在微信公众平台注册的账号，用于为微信用户提供资讯和服务；开发指南分服务端 API 等场景。来源：微信《公众号介绍》（https://developers.weixin.qq.com/doc/subscription/guide/index.html）。
- 注册后账号类型选择后无法更改（协议 2.2）。来源：微信公众平台服务协议。
- 订阅号（二手归纳）：偏资讯传播，个人可注册，消息折叠在订阅号文件夹，每天可群发 1 条（具体次数待核最新规则）。来源：腾讯云开发者社区、数英文章（二手材料）。
- 服务号（二手归纳）：偏业务服务与用户管理，消息展示在会话列表，每月群发 4 条；传统说法为企业/组织主体，认证后可开通微信支付等。来源：同上（二手材料）。
- 公众号可关联小程序：关联后可在菜单、模板消息、客服消息、图文消息中使用小程序。来源：微信《小程序产品定位及功能介绍》第七章。

#### 口径差异

- 口径 A：公众号 = 内容传播与粉丝运营载体。来源：微信官方协议表述。
- 口径 B：公众号 = 轻量产品形态，可做商城、工具入口。来源：行业运营文（二手）。
- 口径 C（待核）：存在「个人服务号」注册路径（服务号助手小程序）。来源：yiban.io 博客（二手，非官方一手）。
- 当前建议：条目 03 以「内容触达 + 引流 + 关联小程序」为主线；若写服务号能力差异，须标注待核个人服务号最新政策。

#### 可用于正文的解释

- 公众号适合：内容驱动获客、建立信任、活动通知、导流到网页/小程序/表单；不是替代完整交互产品的唯一形态。
- 公众号不太适合：复杂交互、强工具属性、需要完整账户体系与交易闭环且仅靠订阅号能力的产品（待大纲界定）。

#### 风险提示

- 订阅号与服务号的能力差异二手材料较多，关键数字（群发次数、支付能力）须事实核查。
- 不要把公众号写成「免费小程序替代品」。

### 3.4 原生 App 是什么及适合什么

#### 基本资料

- 行业定义（二手）：App 是基于 Android 和 iOS 等手机操作系统开发、需安装后使用的应用。来源：人人都是产品经理对比文（二手材料）。
- Apple Developer Program：加入后可构建、测试、分发 App；年会费 99 美元；中国大陆通过 Apple Developer App 注册显示约 ¥688/年自动续期订阅。来源：Apple Developer Program 官网（https://developer.apple.com/cn/programs/）；Apple 支持文档《使用 Apple Developer App 注册》（https://developer.apple.com/cn/support/app-account）。
- 免费 Apple 开发者账户：可获取 Beta 工具、在自己设备上测试，但**不能**通过 App Store 向公众分发。来源：Apple Developer Program 官网「成为 Apple 开发者」对比表。
- Google Play：开发者社区与行业文普遍称 Google Play Console 注册费为一次性 25 美元；免费 App 上架本身不另收年费（应用内购买等另计平台服务费）。来源：SplitMetrics 费用文（二手）；Google Android Developers Play Console 页面（未直接列出费用，待核一手）。
- App 运行环境：操作系统级，可获取更多系统权限（相机、蓝牙、后台任务等，需用户授权）。来源：人人都是产品经理对比文（二手材料）。
- TestFlight：Apple 开发者可邀请外部测试员试用 Beta 构建版本（官方称多达 10,000 名）。来源：Apple Developer Program 官网。

#### 口径差异

- 口径 A：App = 能力最强、成本最高的默认选项。来源：常见行业归纳（二手）。
- 口径 B：App = 特定场景才需要的形态（高频、强系统能力、品牌信任、应用商店分发）。来源：产品分析文（二手）。
- 当前建议：条目 04、06 写「适合什么」而非「永远不要做」；用成本、审核、迭代、获客等维度解释，避免绝对化。

#### 可用于正文的解释

- App 适合：高频使用、强依赖系统能力、需要应用商店信任背书、有明确商业化与团队维护能力的场景。
- App 不太适合（个人第一款角度）：仅验证需求、低频工具、预算有限、无法承担双端开发与持续维护、用户主要在微信生态内的场景。

#### 风险提示

- 开发者账号费用、审核周期、下架规则须以平台最新官方文档为准。
- 不写马甲包、代上架、绕过审核等灰色内容。

### 3.5 第一款产品：网页还是小程序？

#### 基本资料

| 维度 | 网页/H5（归纳） | 微信小程序（归纳） |
|---|---|---|
| 运行环境 | 浏览器等多环境 | 主要在微信内 |
| 触达方式 | URL 链接、二维码、嵌入 | 微信搜索、扫码、分享、公众号关联 |
| 发布/更新 | 通常自行部署即生效 | 每次发版需提交微信审核，通过后手动发布 |
| 开发语言 | 通用 Web 技术栈 | WXML/WXSS/JS 等微信规范 |
| 支付 | 需单独接入（如微信 H5 支付等，条件多） | 企业认证小程序可用微信支付 |
| 个人开发者门槛 | 相对较低（静态页尤甚） | 需注册主体、选类目、过审核；个人无微信支付 |

来源：慕课网 FinClip 科普文、有赞资讯文、阿里云问答、微信官方文档（综合二手+官方，待事实核查逐条确认）。

#### 口径差异

- 口径 A：简单功能两者开发成本差不多，小程序生态组件更统一。来源：慕课网（二手）。
- 口径 B：H5 上线更快、迭代更灵活；小程序长期在微信内体验与转化更好。来源：有赞资讯文（二手）。
- 当前建议：条目 05 用「用户在哪里、要多快验证、要不要微信支付、能不能等审核」四个问题引导，不给唯一标准答案。

#### 可用于正文的解释

- 先问用户主要在哪：微信内 → 倾向小程序；微信外链接/多平台 → 倾向网页。
- 先问要多快改动：频繁试错 → 网页更灵活；功能稳定后做小程序也可。

#### 风险提示

- 对比表不宜写成绝对优劣；个人主体支付限制是关键硬边界。

### 3.6 为什么很多个人项目不适合一开始做 App

#### 基本资料

- 开发与维护：App 通常需同时考虑 iOS 与 Android（或跨端框架），适配成本高于单一 Web 或小程序；行业对比文普遍将 App 列为开发成本最高形态。来源：人人都是产品经理对比文（二手材料）。
- 分发门槛：Apple 公开分发需加入 Developer Program（99 美元/年，中国大陆约 ¥688/年）；Google Play 需注册开发者账号（行业称一次性 25 美元）。来源：Apple 官网；二手费用文。
- 审核与迭代：应用商店审核存在时间不确定；小程序亦需审核，但 App 双端审核+版本碎片化成本更高（定性归纳，待核）。
- 获客：App 安装门槛高于「扫码打开网页/小程序」；个人开发者冷启动更难（定性，本包条目 06 可写机制不讲运营鸡汤）。
- 免费 Apple 账户只能自测，不能 App Store 分发——很多初学者混淆「能跑在手机上」与「能上架」。来源：Apple 官网。

#### 口径差异

- 口径 A：个人开发者永远不要先做 App。来源：部分自媒体（不建议直接采用）。
- 口径 B：App 适合验证后的下一阶段。来源：MVP/产品方法论（二手）。
- 当前建议：正文采用口径 B 的克制版——「不适合一开始」而非「永远不做」。

#### 可用于正文的解释

- 第一款要验证的是需求，不是技术栈虚荣心；App 把成本前置了。
- 账号费、双端、审核、运维都是真实门槛，不是吓唬人。

#### 风险提示

- 避免贬低做 App 的开发者；写「阶段不匹配」而非「选型错误」。

### 3.7 表单工具能不能先验证需求

#### 基本资料

- MVP（最简可行产品）：具备满足早期用户、验证产品理念所需核心功能的最简版本；目标是以最小投入获取真实反馈。来源：Atlassian MVP 指南（https://wac-cdn-a.atlassian.com/zh/agile/product-management/minimum-viable-product）（二手材料）。
- MVP 不一定是软件：可以是视频（Dropbox 案例）、人工代办（Zappos 案例）、落地页、假门测试等。来源：人人都是产品经理 MVP 文（二手材料）。
- 表单/问卷工具：用于收集报名、预约、意向、反馈等结构化数据；国内市场常见腾讯问卷、金数据、问卷星等（行业列举，非官方排名）。来源：人人都是产品经理问卷产品文（二手）；金数据官网案例页（营销材料）。
- 腾讯问卷：微信/QQ 生态内调研场景常被提及；二手材料称其基础功能免费（待核官方最新计费）。来源：人人都是产品经理文（二手）。
- 表单能验证的信号：是否有人愿意填写、留下联系方式、表达付费意愿、选择某选项等。来源：01MVP 手册（二手）；Atlassian MVP 指南（二手）。
- 表单不能替代的：真实使用行为、复杂交互体验、长期留存、完整交易闭环。来源：产品方法论归纳（二手，待大纲界定）。

#### 口径差异

- 口径 A：先上表单 = 偷懒不做产品。来源：部分开发者社区偏见（不建议采用）。
- 口径 B：表单是验证「是否有人要」的低成本实验。来源：MVP 方法论（二手）。
- 当前建议：条目 07 采用口径 B，同时写清边界——适合意向/预约/调研类假设，不适合复杂工具体验验证。

#### 可用于正文的解释

- 想验证「是否有人愿意留下邮箱/报名」→ 表单可能够用。
- 想验证「用户会不会每天用某个复杂功能」→ 表单通常不够。

#### 风险提示

- 具体表单平台功能与收费以各平台官网为准，避免无来源比价。
- 不写「用表单就能创业成功」类话术。

### 3.8 为什么个人项目不要一开始就做复杂

#### 基本资料

- 复杂度常见来源（定性归纳，待核）：用户登录/账号体系、支付与订单、多端同步、后台管理、消息推送、权限系统、数据报表、第三方审核合规等。
- 登录：引入账号体系意味着注册、找回、安全、隐私合规与后续运营责任。来源：系列扩展条目池「个人项目要不要一开始做登录？」（选题参考，非事实来源）；待补专门资料。
- 支付：需主体资质、商户号、接口对接与合规；个人开发者第一款产品常被建议先验证需求再接入。来源：系列选题池主题包 04（边界参考，本文不展开支付教程）。
- MVP 原则：用最低成本验证核心假设；功能齐全 ≠ 验证成功。来源：Atlassian MVP 指南；01MVP 手册（二手）。
- 迭代建议：先做单点功能闭环，再扩展；Dropbox、Zappos 等案例强调分阶段验证（二手案例，慎作绝对归因）。

#### 口径差异

- 口径 A：功能越多越好。来源：初学者常见误区（非权威）。
- 口径 B：先做「最小闭环」。来源：敏捷/MVP 方法论（二手）。
- 当前建议：条目 08 列举 3–5 个「复杂度开关」（登录、支付、后台、多端、审核），解释开了就要维护。

#### 可用于正文的解释

- 每多一个系统，就多一类 bug、多一套运维、多一轮合规。
- 第一款的目标通常是验证，不是架构秀。

#### 风险提示

- 不把「简单」写成「粗糙无体验」；强调 scope 控制。
- 复杂度的具体开发工时无统一来源，正文避免无出处天数/金额。
